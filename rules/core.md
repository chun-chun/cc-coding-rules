# 共用開發規則

本文件適用於不同語言，例子使用中性情境，不引用特定專案名稱、專屬介面或語言語法。語言實作例子放在對應的語言規則；專案實際的檔名、函式與設定用法放在該專案的 `coding-rules.md`。

## 修改範圍與命名

修改前閱讀相鄰實作和專案架構說明，把改動限制在需求涉及的範圍。用領域詞彙描述工作目的。

例如：修正訂單總額計算時，先閱讀計價與折扣的呼叫流程；函式名稱表達「計算訂單總額」，讓呼叫端看得出用途。不要順便重寫無關的登入流程。

## 主流程、共用功能與工具分類

主流程函式代表完整流程或有業務意義的動作。抽出函式應釐清責任或支援重用，避免閱讀流程時頻繁跳轉；單一位置的簡短轉換可留在使用處。不為形式一致增加抽象。

例如：訂單匯入流程負責協調讀檔、驗證與儲存。只用一次的簡短排序可直接寫在流程內，不必另建排序函式。

多個流程需要相同能力時，優先共用實作。共用功能接收完成工作所需的資料，不依賴某個頁面或呼叫端的內部狀態。

例如：匯入與匯出都需要日期正規化時，共用只接收日期資料的正規化函式；不要讓它讀取匯入頁面的輸入框。

與目前檔案責任無關的輔助功能應移出。能分類的放到所屬模組；暫時無法分類、確實可共用且沒有業務編排的小工具，可集中到專案約定的共用工具檔。形成明確類別後再歸類。

例如：日期轉換放進日期工具；尚無明確分類的通用字串清理可先放到專案約定的共用工具檔。訂單匯入流程仍留在訂單模組，不能因為多處使用就放進工具檔。

## 設定與參數群組

可調整的行為應集中在所屬功能的獨立設定檔，或有名稱的參數群組。設定維持單一來源，使用處接收有效設定；單次覆寫不應修改共享預設。

例如：將下載的逾時、重試次數與批次大小 集中為下載設定，傳給下載功能。某次工作需要較長逾時時，建立該次設定，不讓其他工作的逾時一起改變。

路徑由負責該資料的模組依明確基準解析，呼叫端不重複拼接內部目錄。

例如：報表模組依設定的輸出根目錄產生月份子目錄，命令列入口只傳入月份。可從不同工作目錄執行的入口，應驗證解析結果一致。

## 依賴組裝與資源管理

遵循專案的模組責任與依賴方向。建立服務、組裝依賴與執行工作應有清楚邊界；重用外部提供的實例，缺少必要依賴時明確報錯。只有契約允許時，才建立未提供的預設依賴。

例如：批次入口建立一次資料庫連線，交給匯入與驗證工作使用。兩個工作不各自偷偷建立新連線；缺少連線時，回報所需依賴。

由組裝端決定資源的共享範圍與釋放責任。取得服務或資源不應隱含啟用未要求的網路連線、訂閱或寫入。

例如：入口建立並最終關閉共享連線，借用連線的驗證工作不能先將它關閉。只檢查設定的命令，也不應因取得服務就開始下載資料。以替代連線或測試替代實作驗證這些行為。

## 統一日誌與 debug 模式

大型專案應提供共用的日誌與除錯介面，讓各模組用一致方式記錄一般訊息、除錯細節與失敗。debug 開關放在設定檔或參數群組，可依模組控制；輸出附上模組與工作識別。優先使用專案現有機制，避免每個檔案各自維護開關與輸出方式。

例如：一般模式顯示「下載完成，共 300 筆」；開啟下載模組的 debug 後，再顯示請求參數、重試原因與耗時。兩種訊息都經過同一日誌介面，其他模組的 debug 狀態不受影響。測試時可用記憶體中的訊息收集器驗證開關與識別資訊。

記錄重要階段與外部操作的成功、略過或失敗，包含定位問題所需的原因與上下文，避免大量重複輸出。

例如：下載失敗記錄資料來源、批次與原因；重試細節放 debug。不要將每一筆相同失敗都輸出成完整錯誤區塊。

## 結果與錯誤契約

公開介面應明確區分空結果、未要求、部分完成與失敗。依專案慣例傳遞或轉換錯誤，保留定位資訊；刻意忽略錯誤時說明成立條件。

例如：查詢成功但沒有訂單可以回傳空集合；資料庫無法連線則回報失敗，不能也回傳空集合。批次只有部分成功時，結果需包含成功與失敗數量。

## 介面遷移、review 與驗證

修改公開介面時檢查呼叫者，同步更新實作與介面文件。相容分支只保留明確需要的使用情境，遷移完成後移除。

例如：將下載函式的分散參數改為設定群組時，找出命令列、排程與測試的呼叫端一起更新；確認舊入口已無使用者後移除舊參數處理。

使用專案現有的 formatter、lint、型別檢查與測試指令。Review 包含正確性、模組邊界、設定來源、結果契約及主流程可讀性。測試可觀察行為與變更風險，不逐行鏡像實作；交付時記錄實際驗證及結果。

例如：修改重試邏輯時，用替代網路服務驗證重試次數及最終錯誤，不依賴真實外部服務。離線測試要明確隔離連線與輸出位置，不能僅因模式名稱稱為模擬就視為離線。

## Commit 訊息與提交範圍

格式與分類採用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 慣例。該規範明確定義 `feat` 與 `fix`，並允許其他類型；下表的其餘類型是本套選用的常見延伸。英文標題、動詞原形、不加句點，以及同時提供不相容變更標記與遷移說明，都是本套預設，不是官方規範的全部強制要求。

例如：專案可在自己的 `coding-rules.md` 約定中文描述，仍保留 `fix(parser):` 等分類前綴。

預設標題使用英文，格式為 `type(scope): description`；沒有明確範圍時省略 scope，寫成 `type: description`。scope 使用專案約定的模組或功能名稱。描述以動詞原形開頭，說明完成後的具體行為，句尾不加句點；避免只寫 update、fix bug 或 miscellaneous。專案 `coding-rules.md` 可另訂語言、格式與 scope。

例如：`fix(download): preserve retry limit after timeout` 說明修正後保留重試上限；只調整共用文件時可用 `docs: explain configuration ownership`。

依主要目的選擇 type：

| Type | 使用時機 | 例子 |
|---|---|---|
| `feat` | 新增功能或可觀察能力 | `feat(export): support monthly summaries` |
| `fix` | 修正錯誤行為 | `fix(parser): reject incomplete records` |
| `refactor` | 調整結構且不改變外部行為 | `refactor(config): centralize download settings` |
| `perf` | 改善效能 | `perf(search): reuse parsed index` |
| `docs` | 修改文件與文字規則 | `docs: clarify project rule precedence` |
| `test` | 新增或調整測試 | `test(parser): cover empty input` |
| `style` | 僅排版或格式，無行為改變 | `style: apply existing formatter` |
| `build` | 建置、依賴或封裝設定 | `build: update compiler flags` |
| `ci` | 持續整合流程 | `ci: run checks on pull requests` |
| `chore` | 不屬於以上分類的維護工作 | `chore: ignore local workspace files` |

描述不相容的公開契約變更時，在 type 或 scope 後加 `!`，並在本文用 `BREAKING CHANGE:` 說明受影響呼叫者與遷移方式。不要只加符號而省略說明。

例如：標題為 `feat(config)!: require explicit output directory`；本文寫 `BREAKING CHANGE: callers must now provide an output directory; the working directory is no longer used as a default.`。

一次 commit 聚焦一項可獨立檢視的目的，包含該變更必要的程式、測試與文件；無關修改分開提交。不為了區分檔案種類，將同一變更拆成無法正常運作的提交。

例如：修正重試行為時，一起提交修正、對應測試與契約文件；無關的登入頁排版另做 commit。文件規則修改使用 `docs`，不能因為影響未來開發方式就當成產品 `feat`。

簡單變更只需標題；複雜變更在空白行後補充問題、主要做法、實際驗證與必要限制。只記錄確實執行的檢查，未執行時說明原因。

例如：修正逾時重試時，本文說明原本會超過重試上限、現在如何保留計數，以及替代網路服務測試的結果。單純修正文句可只寫標題，不需新增無意義的測試說明。

提交前檢查暫存區的 diff 與格式，確認只包含本次範圍。規則本身不授權自動提交或推送，依當次任務授權執行。

例如：工作目錄同時存在下載修正與使用者未完成的 UI 修改時，只將下載修正相關檔案加入暫存區，再檢視實際提交內容。

預設由 agent 在提交前檢查這些約定，不因採用本規則而自動安裝檢查工具或 Git hook。專案需要自動強制檢查時，另依需求設定。

例如：安裝規則後先由 agent 檢查標題格式；只有專案明確要求時，才加入提交訊息檢查工具與對應設定。

## 規則適用與專案約定

共用規則描述設計目的，語言規則提供該語言的實作方式，不強制所有專案採用同一種表示法。專案根目錄 `coding-rules.md` 中明訂的約定，優先於本套共用規則與語言規則。衝突時依專案約定執行，並指出採用的條文與差異；沒有專案特別約定的部分，繼續遵循共用與語言規則。若專案約定本身不明確，再提出待確認的做法。

例如：共用規則建議可依模組控制 debug，但嵌入式專案的 `coding-rules.md` 明訂受限於空間，只使用編譯時的全域 debug 開關，便採用該專案做法；其他日誌規則仍適用。

例如：集中設定可以用設定檔或具名參數群組實現，不要求所有專案改用相同設定格式。專案已有設定管理機制時，沿用它並在專案文件示範。

專案文件應區分現行做法與待採用提案。現行例子須可由程式或設定核對，提案則說明待實作內容，避免將未完成設計寫成已存在的能力。

例如：目前只有全域 debug 開關時，將模組獨立控制標為提案；待功能完成並驗證後，再更新為現行用法。

## 開發時維護規則

開發中發現現有規則不足、互相衝突或已不符合實作時，主動向使用者提出情境、影響與附例子的修訂草案。區分跨專案原則與本專案約定，取得同意後再修改規則；不要把偶發需求直接升格為全專案限制。

例如：第二個模組開始自行建立 debug 開關時，指出輸出控制已分散，提出統一日誌介面的規則與此專案用法。若專案尚無 `coding-rules.md`，說明可用它記錄具體設定位置與範例，另行取得建立同意。
